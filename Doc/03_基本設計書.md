# Porocia Portal 基本設計書 / 基本定義書

本書は、統合型社内ポータルシステム **Porocia** の基本設計（Basic Design）について詳細に説明するものです。システムアーキテクチャ、プレミアムUI/UXデザイン規則、ディレクトリ構成、データベース詳細設計（Firestoreスキーマ）、セキュリティモデル、および各機能モジュールの詳細設計とフローについて包括的に記述しています。

---

## 1. システムアーキテクチャ / System Architecture

本システムは、高いパフォーマンス、リアルタイム性、および柔軟な拡張性を実現するため、現代的な **サーバーレス・ウェブアプリケーション** モデルを採用し、**Next.js (App Router)** のサーバーサイドレンダリング機能と **Firebase/Firestore** のリアルタイムデータ同期機能を統合しています。

### 1.1 技術スタック / Tech Stack
*   **フロントエンドフレームワーク**: Next.js (App Router), React, TypeScript (厳格モード)
*   **レンダリング戦略 (Rendering Strategy)**: 状況に応じたハイブリッド構成：
    *   **React Server Components (RSC)**: 静的コンテンツ、またはサーバー側で安全にデータを取得する必要がある画面（例：管理者専用ドキュメント一覧、掲示板など）で使用。
    *   **Client Components (RCC)**: ユーザー操作に応じた動的な描画やリアルタイム同期が必要な画面（例：チャット、カレンダー、コメントモーダルなど）で使用。
*   **スタイリング (Styling)**: デザインシステムの基本トークンを定義する **Vanilla CSS** と、レイアウトの高速かつ一貫した構築のための **TailwindCSS** を組み合わせて使用。
*   **データベース (Database)**: Cloud Firestore (NoSQL ドキュメント指向型データベース)
*   **画像・ファイル管理**: Cloudinary SDK (チャット内の画像、ドキュメント内のメディア、プロフィールアバターのアップロードと最適化管理に使用)
*   **主要ライブラリ**:
    *   `react-big-calendar`: カレンダー表示エンジン（Claude風デザインにCSSカスタマイズ）。
    *   `date-fns`: 日付・時刻処理ライブラリ（日本語・ベトナム語の多言語化対応）。
    *   `lucide-react`: クリーンでミニマルなベクターアイコンシステム。
    *   `sonner`: スムーズでプレミアムなトースト通知管理システム。

## 2. UI/UXデザインシステム / UI/UX Design System

Porociaは、Anthropic社の「Claude」のインターフェースにインスパイアされた、**プレミアム＆エディトリアル（Editorial）** なデザイン言語を採用しています。デジタル特有の冷たいダッシュボードではなく、高品質な書籍や学術雑誌を読むような、温かみがあり洗練された空間を構築します。

### 2.1 カラーパレットと役割 / Color Tokens

システム全体に暖色系の中間色（Warm Neutral）を基調とし、アクセシビリティ用のフォーカスリングを除き、冷たいグレーや冷酷なブルーは一切排除しています。

| トークン名 | カラーコード | デザイン上の役割 |
|---|---|---|
| **Parchment** | `#f5f4ed` | メインの背景色。高品質な「羊皮紙」や紙のような質感を表現。 |
| **Ivory** | `#faf9f5` | カードやコンテナの背景色。薄いコントラストでレイヤーの深みを作る。 |
| **Pure White** | `#ffffff` | 主要なアクションボタンや、最大のコントラストが必要な要素に使用。 |
| **Near Black** | `#141413` | プライマリテキストおよびダークテーマ時の背景（オリーブを帯びた優しい黒）。 |
| **Charcoal Warm** | `#4d4c48` | セカンダリアクションボタンのテキストやアイコン。 |
| **Olive Gray** | `#5e5d59` | セカンダリテキスト、説明文などのメタ情報。 |
| **Stone Gray** | `#87867f` | 最も控えめな補助テキスト、脚注、日付表示（サードテキスト）。 |
| **Terracotta Brand**| `#c96442` | アースカラーのテラコッタオレンジ。最も重要なアクション（CTA）に使用。 |
| **Border Cream** | `#f0eee6` | 非常に薄く繊細な境界線。 |
| **Border Warm** | `#e8e6dc` | インタラクティブ要素や大区分の区切りに使用する境界線。 |
| **Focus Blue** | `#3898ec` | インプット要素のフォーカス時の境界線（アクセシビリティ確保用）。 |

### 2.2 タイポグラフィ規則およびシャドウシステム / Typography & Shadow Rules
*   **タイポグラフィの階層**:
    *   *見出し (Headlines)*: 優雅で知的な明朝体・セリフフォント（`Anthropic Serif` または `Georgia`）を使用。見出し全体の調和を保つため、太さは `weight: 500` のみに統一。
    *   *本文・UI要素 (UI/Body)*: 読みやすいゴシック体・サンセリフフォント（`Inter` または `Arial`）を使用。本文の行高（line-height）は余白を持たせて `1.60` に設定。
*   **シャドウシステム (Shadow & Ring)**:
    *   従来の暗いドロップシャドウは使用せず、境界線を表現するような暖かみのある **Ring-shadow** (`0px 0px 0px 1px`) をホバー時に使用。
    *   浮遊するコンテナには、極めて薄いソフトシャドウ **Whisper Shadow** (`rgba(20,20,19,0.04) 0px 4px 24px`) を適用。
*   **角丸（Border Radius Scale）**:
    *   `8px`: 小さなボタン、バッジタグ、小さなカード。
    *   `12px`: 主要ボタン、フォームインプット、検索バー。
    *   `16px` 〜 `32px`: 特徴的な機能カード、メインコンテナ、画像コンテナ、アバターなど。

## 4. データベース設計 / Database Schema (Firestore Schema)

データベースは **Google Cloud Firestore**（NoSQL ドキュメントデータベース）を使用します。以下は主要コレクションおよびサブコレクションの型定義を含む詳細データモデルです。

### 4.1 `users` コレクション
全社員のプロフィール情報を管理します。
*   **ドキュメントID**: Firebase Auth の `uid` と完全に一致させます。
*   **データモデル**:
    ```typescript
    interface UserProfile {
      uid: string;                    // Firebase AuthのUID
      email: string;                  // 社員メールアドレス
      displayName: string;            // 表示名（未設定時はメールのアカウント名）
      photoURL: string;               // Cloudinaryに保存されたプロフィール画像URL
      bio: string;                    // 自己紹介・ステータス
      role: 'admin' | 'member';       // システム内権限（管理者 / 一般社員）
      createdAt: Timestamp;           // アカウント作成日時
      lastLoginAt: Timestamp;         // 最終ログイン日時
    }
    ```

#### `readState` サブコレクション (`users/{uid}` 配下)
ユーザーごとのチャットルーム既読状態を追跡します。
*   **ドキュメントID**: `channelId` (チャットルームID)
*   **データモデル**:
    ```typescript
    interface ReadState {
      lastReadAt: Timestamp;          // 対象チャットルームを最後に開いた時刻
      lastReadMessageId: string;      // 最後に読んだメッセージのドキュメントID
    }
    ```

---

### 4.2 `channels` コレクション
チャットルーム（公開チャンネル、プライベートグループ、1対1のDM）を管理します。
*   **ドキュメントID**: Firestoreによる自動生成（DMの場合は特定ルールで生成）。
*   **データモデル**:
    ```typescript
    interface Channel {
      id: string;                     // チャットルームID
      name: string;                   // チャンネル名（例：「開発チーム」）
      description: string;            // ルームの説明
      type: 'public' | 'private' | 'dm'; // ルーム種別（公開、非公開グループ、DM）
      createdBy: string;              // 作成者のUID
      isArchived: boolean;            // アーカイブ状態（非表示フラグ）
      members: string[];              // ルームに所属する全メンバーのUID配列
      unreadCount: Record<string, number>; // 各メンバーの未読件数マップ（UID -> 未読件数）
      createdAt: Timestamp;           // 作成日時
    }
    ```

#### `messages` サブコレクション (`channels/{channelId}` 配下)
チャットルーム内のメッセージ履歴をリアルタイムで管理します。
*   **ドキュメントID**: 自動生成。
*   **データモデル**:
    ```typescript
    interface ChatMessage {
      id: string;                     // メッセージID
      text: string;                   // メッセージの本文
      senderId: string;               // 送信者のUID
      senderEmail: string;            // 送信者のメールアドレス
      senderName: string;             // 送信時の送信者名（キャッシュ）
      senderPhotoURL?: string;        // 送信時のプロフィール画像URL
      type: 'text';                   // メッセージタイプ
      createdAt: Timestamp;           // 送信日時
      updatedAt: Timestamp | null;    // 編集日時（未編集時はnull）
      readBy: string[];               // このメッセージを読んだユーザーのUID配列
      readAt: Record<string, Timestamp>; // 各ユーザーが読んだ日時のマップ（UID -> 読了日時）
      replyTo?: {                     // スレッド返信情報（対象メッセージ情報）
        messageId: string;
        senderId: string;
        senderName: string;
        senderPhotoURL?: string;
        text: string;
      } | null;
      reactions?: Record<string, string[]>; // 絵文字リアクションマップ（Emoji -> UID配列）
    }
    ```

### 4.3 `articles` コレクション (ナレッジベース / Wiki)
社内規定、技術ドキュメント、業務マニュアル（Markdown形式）を管理します。
*   **ドキュメントID**: 自動生成。
*   **データモデル**:
    ```typescript
    interface Article {
      id: string;                     // ナレッジID
      title: string;                  // タイトル
      content: string;                // Markdown形式の本文
      summary: string;                // 一覧に表示する概要
      category: 'hr' | 'engineering' | 'design' | 'onboarding' | 'sales'; // カテゴリ
      tags: string[];                 // 検索補助用タグ配列
      scope: 'all' | 'group' | 'admin'; // 公開範囲制限
      allowedGroups?: string[];       // scopeが 'group' の場合に閲覧可能なグループID一覧
      views: number;                  // 総閲覧数
      likes: string[];                // いいねをしたユーザーのUID配列
      createdBy: string;              // 執筆者のUID
      authorName: string;             // 執筆者名
      authorPhoto?: string;           // 執筆者のプロフィール画像
      createdAt: Timestamp;           // 作成日時
      updatedAt: Timestamp;           // 最終更新日時
    }
    ```

#### `comments` サブコレクション (`articles/{articleId}` 配下)
記事の下部に投稿される社員間の質問やディスカッションコメントを管理します。
*   **ドキュメントID**: 自動生成。
*   **データモデル**:
    ```typescript
    interface ArticleComment {
      id: string;                     // コメントID
      userId: string;                 // 投稿者のUID
      userName: string;               // 投稿者名
      userPhoto?: string;             // 投稿者のプロフィール画像
      text: string;                   // コメント本文
      createdAt: Timestamp;           // 投稿日時
    }
    ```

## 5. セキュリティと権限設計 / Security & Authorization Design

Porociaは多層防御アプローチを適用し、システム全体を保護しています。
1.  **クライアント層（Middleware & Routing）**: 未認証ユーザーのシステム侵入を防ぎ、管理者以外のページ（`/admin`など）へのアクセスを動的に制限します。
2.  **データベース層（Firestore Security Rules）**: データベースへの直接の読み書きを細粒度で制御する、サーバーレスアーキテクチャの最終防衛線です。

### 5.1 Firestoreセキュリティルール（サンプル）
Firestore内の各コレクションに対する基本的なアクセスルール設計は以下のようになります。

```javascript
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    
    // 補助関数: 認証済みユーザーか確認
    function isSignedIn() {
      return request.auth != null;
    }
    
    // 補助関数: 要求ユーザーのロール情報を取得
    function getUserRole() {
      return get(/databases/$(database)/documents/users/$(request.auth.uid)).data.role;
    }
    
    // 補助関数: 管理者権限か確認
    function isAdmin() {
      return isSignedIn() && getUserRole() == 'admin';
    }

    // 1. usersコレクションの保護
    match /users/{userId} {
      allow read: if isSignedIn();
      allow write: if isSignedIn() && (request.auth.uid == userId || isAdmin());
      
      // readStateサブコレクション：本人のみ読み書き可能
      match /readState/{channelId} {
        allow read, write: if isSignedIn() && request.auth.uid == userId;
      }
    }

    // 2. channelsおよびmessagesコレクションの保護
    match /channels/{channelId} {
      allow read: if isSignedIn() && (
        resource.data.type == 'public' || 
        request.auth.uid in resource.data.members || 
        isAdmin()
      );
      allow create: if isSignedIn();
      allow update, delete: if isSignedIn() && (
        request.auth.uid == resource.data.createdBy || 
        isAdmin()
      );
      
      match /messages/{messageId} {
        // 所属するルームのメンバーのみメッセージの読み書きを許可
        allow read, write: if isSignedIn() && (
          request.auth.uid in get(/databases/$(database)/documents/channels/$(channelId)).data.members || 
          isAdmin()
        );
      }
    }

    // 3. articlesコレクションの保護
    match /articles/{articleId} {
      allow read: if isSignedIn() && (
        resource.data.scope == 'all' ||
        isAdmin() ||
        (resource.data.scope == 'group' && hasGroupAccess(resource.data.allowedGroups))
      );
      allow create: if isSignedIn();
      allow update, delete: if isSignedIn() && (
        request.auth.uid == resource.data.createdBy || 
        isAdmin()
      );
    }
    
    // グループ閲覧権限のチェックロジック（実際の実装に即した検証）
    function hasGroupAccess(allowedGroups) {
      return isSignedIn(); 
    }
  }
}
```

## 6. 機能詳細設計および業務フロー / Functional Design & Workflows

### 6.1 リアルタイムチャットおよび既読管理機能 (Chat & Read Receipts)
*   **メッセージ送信プロセス (一括トランザクション - Batch Write)**:
    不整合を防ぐため、メッセージ送信処理は以下のステップで一括書き込み（Batch）として実行されます。
    1.  `messages` サブコレクションに新しいドキュメントを作成。この際、`readBy` にはあらかじめ送信者のUIDを格納。
    2.  `channels` ドキュメントの `members` フィールドに対して `arrayUnion` で送信者のUIDを結合（送信者がルームの所属員であることを保証）。
    3.  Firestoreの `increment(1)` 関数を用い、送信者以外のルームにいる全メンバーの `unreadCount[memberUid]` カウンタを一斉に加算。
*   **既読設定プロセス (Mark as Read)**:
    ユーザーがチャットルームを開いた際：
    1.  `messages` サブコレクションの最新ドキュメントを取得。
    2.  メッセージの `readBy` 配列に自身のUIDが含まれていない場合、UIDを配列に追加し、`readAt[uid]` に現在時刻を設定。
    3.  ユーザー個人の `users/{uid}/readState/{channelId}` の時刻情報とメッセージIDを更新。
    4.  対象のチャットルーム上の自身に対する `unreadCount[uid]` を `0` にリセット。
*   **1対1のダイレクトメッセージ (DM)**:
    DM用チャットルームのIDは、2名のユーザーのUIDをアルファベット順にソートして自動的に結合した一意のフォーマット `dm_uidA_uidB` を用います。`ensureDirectChannel` APIが、起動時に既に存在するかを確認した上で必要に応じて自動生成します。

### 6.2 カレンダー機能 (Calendar)
*   **2カラム型カレンダー画面設計**:
    *   *サイドバー (Sidebar)*: 当月ハイライト用のミニカレンダー、およびカテゴリ（会議、来客、締切、イベント）や公開範囲によるフィルタリングスイッチを設置。
    *   *メイングリッド (Main Grid)*: 週・月・日別のスケジュール配置グリッドを表示。
*   **表示スコープ制限**:
    予定の表示は、作成時に入力された `scope` パラメータに応じて Firestore レベルで事前にクエリフィルタリングされます。
    *   `company`: 社内全員に公開。
    *   `group`: スケジュールの `groupId` が所属グループに該当するユーザー（または管理者）にのみ公開。
    *   `personal`: 他のメンバーからは完全に遮断されます。データベースのクエリで `createdBy === CurrentUID` である場合のみ描画されます。

### 6.3 ナレッジベース機能 (Knowledge Base - Wiki)
*   **エディタとビューアーの仕組み**:
    *   リアルタイムにマークダウン構文をプレビュー可能な分割型画面（Split-screen Editor）を提供。
    *   閲覧ページでは、記事本文の `H2` および `H3` タグをフロントエンド側で動的に解析し、右側に追従式の目次（Table of Contents）メニューを自動構築。
    *   文字数から想定読了時間を自動計算する処理を搭載 (`文字数 / 500文字 = 読了時間（分）`)。
*   **Cloudinaryを利用したアセット管理**:
    *   ドキュメント作成中、ユーザーが画像ファイルをアップロード（「Thêm ảnh」ボタン押下）すると、クライアント側からCloudinary API (`https://api.cloudinary.com/v1_1/.../image/upload`) に対し **Unsigned Upload Preset** (`porocia`) を用いて**ブラウザ直接アップロード**を同期実行します。
    *   アップロード成功後、安全なアセットURLを含むマークダウン構文 `![image](cloudinary_url)` がエディタのカーソル位置（selection pointer）に即時挿入されます。
    *   管理者や著者がドキュメントを完全削除する際は、サーバー側API (`src/lib/firebase/cloudinary.ts`) が本文内のCloudinaryアセットの正規表現による検出を行い、署名付きAPIリクエストを介してCloudinary上の画像アセットを同時にクリーンアップし容量を節約します。

### 6.4 社内掲示板機能 (Announcements)
*   **掲示板ピン留めおよびソート要件 (Pinning Logic)**:
    *   管理者は、重要なお知らせを一番上に固定（Pin）できます。
    *   掲示板一覧の取得時、Firestoreは `isPinned DESC`（ピン留めが最上部）かつ `createdAt DESC`（新着順）の複合インデックスでソートされたクエリ結果を返し、社員に最重要情報を見逃させない仕様とします。
*   **カレンダーイベント連携**:
    *   日付に関連するお知らせを登録する際、自動的に全社向けカレンダーに同期（`calendarEventId` で紐付け）する機能を提供します。どちらかで更新または削除された場合、カレンダー側のスケジュール予定も同時に更新・削除が行われます。

## 7. テストおよび検証計画 / Test & Verification Plan

設計通りにシステムが完全に機能するかを保証するために、以下の手順で自動および手動の検証を実施します。

### 7.1 自動テスト (Automated Tests)
1.  **ユニットテスト (Firestoreエミュレータ)**:
    *   Firebase Emulator Suiteを用いて、セキュリティルール（Firestore Security Rules）の動作を網羅的にテストします。
    *   正しい権限のユーザーのみがメッセージを書き込めるか、カレンダー予定の作成・削除が保護されているか、未読件数カウンタがメッセージ送信時に排他制御（increment）で正確に処理されるか等を検証します。
2.  **統合テスト (Next.jsミドルウェア & ルーティング)**:
    *   CypressまたはPlaywrightによるE2E統合テストを実行します。非ログイン状態で `/calendar` や `/admin` などの認証ガードルートにアクセスした際に、Next.jsのミドルウェアが適切に検出し `/login` に自動転送されることを検証します。

### 7.2 手動テストおよび検証 (Manual Verification)
1.  **複数端末・複数ロール間での同期検証**:
    *   2つの異なるブラウザ（シークレットウィンドウ含む）で、それぞれ「管理者（Admin）」と「一般社員（Member）」のアカウントにログインし、リアルタイムでのDM送信・受信時の通知や既読同期（unreadCountのリアルタイム変化）を手動検証します。
2.  **マルチデバイス・レスポンシブデザイン確認**:
    *   Chrome Developer Toolsを用い、タブレット幅（768px 〜 991px）およびPC表示幅において、カレンダーの2カラムレイアウトやナレッジのツリー表示が型崩れせず、適切に表示されることを確認します。
